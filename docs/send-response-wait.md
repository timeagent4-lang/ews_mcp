# 邮件发送的 30 秒等待上限

`send_draft` 每次工具调用最多等待业务处理 30 秒，包含 OA 校验、Exchange 连接、草稿读取、发送及回执读取。30 秒内得到结果时按原合同返回；没有取得最终结果时，先结束本次等待。

这项上限只用于 `send_draft`，不是全部工具的全局超时。调用方与反向代理的超时应大于 30 秒并预留通信余量，避免在服务返回前先断开。

## 确认发送仍在处理

确认请求已经携带 `operation_id`。等待超过 30 秒时，服务返回：

```json
{
  "ok": false,
  "status": "processing",
  "operation_id": "原操作号",
  "results": null,
  "wait_timed_out": true,
  "note": "请求尚未取得最终结果，后台处理可能继续。请勿重新发送，仅用原操作号查询回执。"
}
```

此时 MCP `isError=false`；`ok=false` 表示尚未取得业务成功结果。调用方应展示“处理中”，不要展示“发送成功”或“发送失败”。

`processing` 是本次请求的等待状态，**不是数据库中的执行状态，也不证明身份校验、确认或发送已完成**。等待可能发生在 OA、连接、发送或回执查询阶段。超时响应只带调用方已提供的操作号，不读取或暴露未经校验的回执。

已经开始的工作线程可以继续运行，正常经过身份与权限校验、原子确认、发送和回执持久化。等待超时不会把操作改为 `failed` 或 `unknown`，也不会启动一次新的发送。若工作线程尚未获得运行机会，本次请求可能尚未执行；以重新校验身份后查到的回执为准。

## 查询最终结果

使用同一工具，在扁平 `arguments` 中传入 `lanid` 和原操作号，不携带确认令牌、草稿 ID 或其他业务参数。邮箱仅来自 OA 按 LANID 查询的唯一结果，仍检查结果唯一性和邮箱有效性；`name` 仅为可选兼容字段，传入时忽略，不用于验证或授权：

```json
{
  "lanid": "员工 LANID",
  "operation_id": "原操作号"
}
```

查询仍执行 OA 校验和邮箱／工具归属检查，不连接 Exchange。读取最终回执即可停止查询，不要高频轮询。

- `completed`：发送调用已成功返回，读取其结果；这不等于收件人已收信或阅读。
- `executing`：操作已开始，继续等待并稍后查询。
- `pending`：原预览尚未被成功确认执行，不能解释为邮件已发送。
- `failed`：保留现有的明确拒绝语义，读取错误原因。
- `unknown`：可能已经发送，禁止自动重发；需核查实际发送状态。
- `processing`：本次回执查询本身也达到 30 秒等待上限，尚未拿到已校验的回执。

重复确认正在执行、已完成或结果未知的原操作，不会再次调用发送。

## 预览超时

没有 `operation_id` 的预览请求若超过 30 秒，返回 `RESPONSE_WAIT_TIMEOUT`，MCP `isError=true`，不伪造操作号或确认令牌。本次预览不会发送邮件；后台预览可能完成并留下未执行的待确认记录。可重新请求预览；如果原请求使用了 `idempotency_key`，继续使用原值。

## 与 EWS 网络超时的区别

`EWS_MCP_HTTP_TIMEOUT` 仍是每次 EWS 网络请求的连接／读取超时，默认和空值回退为 300 秒。它不是整个工具调用的总耗时；多次请求、OA 和 SDK 等待会累加。本次新增的 30 秒上限控制用户等待，不强制终止 Exchange 请求。

后台最终得到明确响应时继续保存回执；实际发送发生网络超时或其他不明确错误时，仍按原逻辑记录 `unknown`。进程重启或退出不能保证后台工作继续；保留原操作号并按现有恢复机制核查，勿重发。

AnyIO 的线程取消机制只结束等待，不能强制终止已经运行的线程，参见 [线程文档](https://anyio.readthedocs.io/en/stable/threads.html)和[超时文档](https://anyio.readthedocs.io/en/stable/cancellation.html)。
